1. Overall project summary

UMNAAPP is a full-stack India-oriented mapping platform: authenticated React/Vite PWA, Express/Prisma/PostGIS API, separate admin SPA, public embeddable maps API + JS SDK, Docker Compose for Postgres (PostGIS), Redis, TileServer, OSRM, Nominatim, and Nginx.

What ships today

  • Email OTP + Google OAuth login sessions
  • MapLibre map with search, routing, turn-by-turn + voice
  • Community places (CRUD, approval, duplicates, reviews, photos, claims, labels)
  • Favorites, festivals, polygon explore, measure, utilities
  • Safe-route scoring + hazard reports (admin-moderated)
  • Live location share links + Socket.IO
  • In-app + Web Push notifications
  • Admin moderation, legal docs, schema/data explorer
  • PWA install + offline raster tile packs
  • Public REST + embed map + sdk.js

Architecture snapshot

  • Frontend: React 18, Vite, Tailwind, MapLibre, Socket.IO client, PWA
  • Backend: Express, Prisma, JWT sessions, Passport Google, web-push
  • DB: PostgreSQL + optional PostGIS geom / GiST
  • Admin: Separate Vite app, shared ADMIN_SECRET
  • Infra: Docker Compose; defaults often hit umnaapp.in / public OSRM/Nominatim
  • Mobile: PWA only — no Capacitor project in repo
Verification method: Routes, controllers/services, Prisma models, and frontend call sites were cross-checked. 3. Feature-wise working process & functionality

Each block: process → status → score → pros/cons from verified code paths.

3.1 Authentication

Working 7.0 / 10
Working process
  1. User registers or logs in via LoginPage / RegisterPage → POST /api/auth/register|login.
  2. Backend stores bcrypt-hashed OTP in OTPVerification, emails via SMTP (atozasAuth).
  3. OTPVerificationPage → POST /api/auth/verify-otp → JWT + Session row.
  4. Google: GET /api/auth/google (Passport) → callback redirects with ?token= → AuthContext.
  5. Subsequent API calls use Authorization: Bearer; middleware checks JWT and live session.
  6. Logout deletes session server-side; 401 on /auth/me clears client session.

Functionality: Primary path is complete. Register password is hashed but never used for login. LoginPageAtozas is not routed. Kit POST /api/google returns 501. Dual OTP writers on same table if kit routes are used.

Pros
  • Session revocation on logout
  • Hashed OTPs
  • Google HMAC state
Cons
  • Token briefly in URL (Google)
  • Dead Atozas UI / 501
  • SMTP dependency for OTP

3.2 Interactive map

Working 8.5 / 10
Working process
  1. HomePage mounts MapComponent (MapLibre GL).
  2. Street tiles from umnaapp / env / /api/map/tiles with Carto Voyager fallback; satellite (ArcGIS) & terrain overlays.
  3. Markers/layers for places, search hits, routes, hazards, utilities, live share, vehicles.

Functionality: Fully interactive. Local Docker TileServer is optional and unused unless env points to it.

Pros
  • Resilient tile fallbacks
  • Rich overlay model
Cons
  • Hardcoded production tile hosts
  • India-centric defaults

3.3 Search & geocoding

Working 8.0 / 10
Working process
  1. SearchBar debounces → GET /api/map/search-simple.
  2. unifiedTextSearch: local Place DB ± OSM tables ± HTTP geocoders (umnaapp / public Nominatim).
  3. Results plotted; reverse geocode via /api/map/reverse.

Functionality: End-to-end. Quality degrades if upstreams fail; SearchBar does not always pass map bias lat/lng.

3.4 Place management, approval, duplicates, extract

Working 8.5 / 10
Working process
  1. Add: AddPlaceModal → reverse geocode → optional translate → duplicate check → POST /map/places (pending + autoApproveAt).
  2. Scheduler every 15 min auto-approves expired pending places; admin can approve/reject earlier.
  3. Visibility: approved public; pending owner-only.
  4. Extract: Google NearbySearch client-side → daily grid-extract/consume → POST /places/bulk.
  5. Detail panel: contribute fields, nearby, history; ownership-aware edit/delete.

Functionality: One of the strongest areas. Duplicate index (googlePlaceId / coords / name+address) is enforced on create and bulk.

Pros
  • Audit trail
  • Auto-approve off hot path
  • Strong dup logic
Cons
  • Extract needs Google key/quota
  • Photos stored as data URLs

3.5 Favorites, reviews, photos, claims, labels

Partial 7.7 / 10
Working process
  1. Favorites: GET/POST/DELETE /map/favorites — bookmark only, no Place create.
  2. Reviews/photos: CRUD on DB places; one review per user; photos capped (~10, size limit).
  3. Claims: user submits → admin approve stamps claimedById; reject path exists.
  4. Labels: private per-user PlaceLabel.

Functionality: Favorites/labels/reviews work. Photos work but store base64 in DB. Claims moderation works, but notification on approve/reject uses raw prisma.notification.create (no Socket.IO / web push / preference check) — Partial for claim UX completeness.

3.6 Navigation, routing & voice

Working 8.0 / 10
Working process
  1. RoutePanel → GET /api/map/route with profile (driving/walking/cycling/bus/two_wheeler/train).
  2. Backend tries ROUTE_SERVICE_URL (default umnaapp OSRM) → OSRM_URL → public OSRM → straight-line fallback.
  3. Start navigation → NavigationView + useVoiceNavigation (snap, phases, off-route reroute, Web Speech).

Functionality: Real turn-by-turn for road profiles. Bus / two-wheeler / train retime driving geometry — not true transit graphs. Voice quality is browser-dependent.

3.7 Safe route & hazard reports

Partial 7.0 / 10
Working process
  1. Score alternatives via POST /map/safe-route/score (hazards + road heuristics + avoid options).
  2. Users report via HazardReportSheet → pending SafetyHazardReport → admin approve.
  3. During nav, useSafeRouteMonitor can warn / suggest safer alt.

Functionality: Code path complete. With zero approved hazards, ranking falls back to heuristics (fallback: true) — useful but not “community safety” yet.

3.8 Live location sharing

Working 8.5 / 10
Working process
  1. Create share → timed token → GPS updates via socket live-location:update.
  2. Viewer opens /live/:token → exchange → join room → live marker + viewer bar.
  3. Stop/expire/rotate token; pause on owner disconnect; viewer notifications.

Functionality: Fully wired REST + Socket.IO + Prisma. Requires correct proxy/WebSocket config in production.

3.9 Vehicle tracking

Partial 5.0 / 10
Working process
  1. Backend: full /api/vehicles CRUD + location history; Socket.IO vehicle rooms.
  2. Map listens for vehicles:list / location updates and draws markers.

Functionality: README claims real-time vehicle tracking. There is no dedicated frontend page/UI to create or manage vehicles — backend-capable, product-incomplete.

3.10 Notifications

Partial 7.0 / 10
Working process
  1. In-app list/unread via /api/notifications; live via Socket.IO; prefs in Settings.
  2. Web Push: VAPID public key → subscribe → web-push delivery when enabled.
  3. Events: place submitted, community place added (opt-in), place approved, festivals, live-location events.

Functionality: Solid for place/live events. Claim approve/reject skips createUserNotification. Festival / place_added can fan out to all opted-in users (not geo-scoped despite “near you” copy).

3.11 Admin panel

Working 7.5 / 10
Working process
  1. Admin SPA authenticates with shared ADMIN_SECRET (Bearer / X-Admin-Key), stored in localStorage.
  2. Dashboard counts/growth; pending & extracted places; claims; hazards; legal docs; schema; read-only data explorer.

Functionality: Moderation is complete and useful. No per-admin RBAC. Data explorer can return password hashes, session tokens, OTPs; ?full=1 can dump large blobs.

3.12 Ask Maps & map assistant

Partial 7.0 / 10
Working process
  1. POST /map/ask: Groq intent if GROQ_API_KEY, else keyword fallback → place search.
  2. POST /map/assistant: Groq chat or offline FAQ mode.

Functionality: Real integration with graceful degrade — not a stub, but “AI product” quality is env-dependent.

3.13 Polygon explore, measure, utilities, festivals

Working 8.0 / 10
Working process
  1. Polygon → POST /map/places/in-polygon (PostGIS or JS fallback) + search enrichment.
  2. Measure → client haversine path on map (no backend).
  3. Utilities → GET /map/utilities/nearby (OSM amenities when configured).
  4. Festivals → GET /map/festivals/upcoming from Place festival fields.

Functionality: All implemented. Utility finder & festivals are data-dependent; USP catalog still marks some as “Not started” (stale vs code).

3.14 PWA, offline maps & mobile

Partial 6.5 / 10
Working process
  1. vite-plugin-pwa + custom sw.js: precache shell; CacheFirst tiles; NetworkOnly for auth/admin/notifications.
  2. OfflineMapsSheet downloads viewport tiles to Cache API + IndexedDB region metadata.
  3. Install prompts via landing / install manager; update & offline banners in PwaShell.

Functionality: PWA install + offline raster viewing works. Offline turn-by-turn and vector tiles are Missing. No Capacitor Android project despite Asset Links placeholder for com.umnaapp.app.

3.15 Public maps platform (embed + SDK + REST)

Working 7.5 / 10
Working process
  1. Hosts/paths like maps.* / /embedded-map → PublicMapPage (no auth shell).
  2. Open-CORS /api/public/* for places, search, nearby, route, legal; /sdk.js served by backend.
  3. Socket namespace /public-maps broadcasts approved place changes.

Functionality: Usable developer surface. Phase 10 (API keys, usage analytics, developer dashboard) explicitly deferred — open public API is a trust/abuse risk at scale.

3.16 Profiles, i18n, feedback, settings

Working 7.5 / 10
Working process
  1. Settings: profile, picture (data URL), notification prefs, privacy.
  2. My Contributions + public profile with profilePublic gate.
  3. Language via atozas-traslate + Indic dictionaries; voice maps en/kn/hi (+ Tulu→Kannada TTS).
  4. Feedback modal posts to /api/feedback.

Functionality: Complete for MVP. Translation coverage is partial across all strings; picture storage shares the same base64 scaling issue as photos.

7. Priority-wise recommendations

P0
Hardening before go-live

Disable/mount /api/test only when NODE_ENV !== 'production'. Enforce strong secrets; require Redis for rate limits in prod; verify SMTP/VAPID/Google/OSRM env on staging smoke tests.

P1
Correctness & trust

Fix claim notification path; redact admin explorer fields; migrate admin auth off localStorage; move photos/avatars to object storage + URLs.

P2
Product completeness

Ship vehicle management UI or stop advertising it; geo-target broadcasts; complete or remove Atozas kit paths; add API keys for public platform; expand i18n coverage; shared UX error/toast layer.

P3
Differentiation roadmap

Offline routing, hyperlocal categories, pilgrimage packs, verified local moderators, embeddable collections — pick 2–3 USP catalog items and execute rather than spreading thin across the full CSV.

8. Final conclusion

UMNAAPP is a substantially implemented mapping product — not a UI mock. Places, search, routing, live share, admin moderation, PWA offline packs, and public embed form a coherent MVP with real India-oriented potential (product potential 8.5/10).

The gap to a trustworthy production rating is operational and security maturity, not feature imagination: test-route exposure, optional rate limits, media-in-DB, incomplete claim push delivery, and overstated readiness docs. Vehicle tracking and native mobile are the clearest “advertised vs shipped” mismatches.

Score interpretation

  • 9–10: Production-hardened, scalable, secure
  • 7–8: Strong MVP, fix P0/P1 before scale
  • 5–6: Partial / prototype in area

Pros (project-level)

  • Deep place contribution system with approval, duplicates, audit, claims, reviews
  • Practical map stack with graceful external fallbacks
  • Live location + Socket.IO done properly
  • Admin tools that operators can actually use
  • PWA + offline tile packs ahead of many map startups
  • Public embed/SDK opens distribution channel

Cons (project-level)

  • Security posture not matching feature maturity
  • Scalability cliffs (base64 media, notify fan-out, single process)
  • Dead code / dual auth paths add maintenance risk
  • Heavy dependence on umnaapp.in / public OSRM/Nominatim unless self-hosted data prepared
  • USP catalog and prod-readiness docs drift from code reality
  • Limited automated tests

Bottom line: Treat UMNAAPP as a feature-complete community map MVP with excellent product direction. Close P0/P1 security and notification gaps, then invest in 2–3 differentiators (offline routing, hyperlocal data, public API keys) to move from ~7.2 toward a true 9+.
